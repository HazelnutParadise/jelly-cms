# 系統維運

系統工具限管理員使用。完整端點與欄位見[工作單 08](tickets/08-system.md)。

## 設定、日誌與搜尋引擎

`/admin/settings` 會前往網站設定。閱讀與網址、爬蟲、留言、郵件、快取與佇列、更新各有獨立分頁；轉址位於 `/admin/redirects`，系統日誌位於 `/admin/logs`。

設定只接受已登記的鍵，秘密欄位讀取時遮罩，留空保留，勾選清除才移除。程式碼注入與備份下載、還原、套用更新等操作，需要管理員的瀏覽器登入與同源寫入證據，不能改用 Bearer 權杖。

網站位於反向代理後時，設定 `APP_URL` 為公開來源。IndexNow 使用這個來源建立內容網址，內容寫入與待通知紀錄在同一筆資料庫交易完成，派送失敗後由背景工作重試。草稿、私密內容與不索引內容不會送出。

`noindex`、AI 使用偏好與 robots 規則由網站設定及單篇覆寫共同決定。這些規則不取代登入與內容權限。

## 快取、佇列與郵件

預設使用記憶體快取與 PostgreSQL 佇列。後台可改用 Redis／Valkey；NATS JetStream 需先以 build tag 編譯：

```sh
go build -tags nats -o jelly-cms ./cmd/server
```

`JELLY_CACHE_URL`、`JELLY_QUEUE_URL`、`JELLY_QUEUE_WORKERS` 優先於後台設定。連線資訊加密保存，設定 API 不回傳明文。修改工作者數量後需重新啟動，才會使用新的數量。

切換佇列前會保護執行中的工作，再以原工作 ID 搬移等待中的工作。切換紀錄保存於資料庫，程序中斷後會先復原切換，再接收及執行新工作。後端不可用或復原未完成時，請修復連線並查看日誌，不要刪除內部紀錄強制切換。

郵件測試、備份、匯入與更新等操作會回傳 `202` 及工作編號。這表示已排入處理，可到「快取與佇列」的工作列表查看結果。SMTP 測試信真的投遞成功後，工作才標示完成。

## 附件儲存策略

在 `/admin/media/policies` 管理本機、S3 與外掛儲存策略。搬移會回傳背景工作編號，完成後保留附件 ID。兩個策略使用同一儲存位置時，不會因策略設定或憑證不同而刪掉共用的原檔；撞名時另建路徑並保留既有附件。

同一 S3 位置只更換策略時，系統會先用目標策略讀取附件，核對大小與既有 SHA-256，再切換資料列。目標憑證、區域或讀取內容驗證失敗時，保留原策略與原檔。

## 備份與還原

在 `/admin/tools/backup` 選擇資料庫、附件與設定後建立備份。封存檔以 AES-GCM 加密，存於不公開的 `data/backups/` 或選定的備份用途策略，不放在 `/uploads`。`data/config.json` 不納入封存，請另行保存資料庫連線設定；只有輸入通關密語時才會包含 `auth-secrets.json`。

遠端目的地會在建立備份紀錄時固定，之後修改預設備份目的地不影響已排入的工作。上傳後會讀回並核對大小與 SHA-256，確認一致後才標示完成。失敗的遠端傳輸可重試同一份封存；下載、驗證與還原會在需要時取回遠端封存並再次核對。

仍被附件或備份引用的策略，不能刪除或修改目的地。可以更名及輪替憑證；刪除前須先處理引用它的資料。

排程備份按網站時區計算每日保留，並加上設定月份內的每週保留。手動與還原前備份受到保護。本機保留只會清除已驗證遠端副本的排程封存；下載及遠端讀回另有權限為 `0700`／`0600` 的 `.private-cache`，目前不會自動清除這份快取。

還原時輸入 `RESTORE` 及封存通關密語。系統先建立還原前備份、開啟維護模式，再驗證封存、還原資料庫及檔案。還原失敗時會保留復原紀錄，下一次啟動先完成復原；無法確認資料一致時會停止啟動。不要刪除復原紀錄來跳過檢查。

## 從 WordPress 匯入

在 `/admin/tools/import` 上傳 `.xml`、`.xml.gz` 或 `.zip` 的 WXR，單檔上限 512 MiB。先設定作者與內容類型，再預跑檢查衝突，確認後執行。匯入作者會建立為受邀帳號；重跑依匯入對照資料去重，舊網址建立轉址。

頁面會自動刷新執行狀態，有未儲存的輸入時暫停刷新，兩分鐘後可手動重新整理。完成報告分別列出已建立的內容與略過原因。遠端附件仍受私有位址、大小與逾時限制。

## 更新獨立執行檔

`/admin/settings/update` 會依執行方式顯示操作。容器、Kubernetes 與套件管理安裝，請依頁面指令換版；只有可寫入的獨立執行檔能在後台套用更新。

發布執行檔時，Release workflow 會把 `MINISIGN_PUBLIC_KEY` 的公鑰行嵌入執行檔。自行編譯而沒有嵌入公鑰的版本會拒絕套用更新。這個公鑰須對應發布流程簽署 `checksums.txt` 的私鑰；私鑰不能放進執行檔。

套用順序為下載、驗證 SHA-256 與 minisign、檢查封存內容、建立本機資料庫備份、替換執行檔與 web、檢查新執行檔。備份失敗就不替換。更新備份固定為本機、資料庫內容與手動備份種類，並記錄工作 ID 及目標版本；同一工作重試只重用驗證通過的備份。

新執行檔檢查失敗時，還原舊執行檔及 web。成功後由 Unix 自我替換程序，Windows 啟動新程序後結束舊程序；外部監督程式仍需允許重新啟動。下一次正常啟動會先遷移資料庫並綁定 HTTP，再確認啟動成功。連續兩次啟動失敗會嘗試退回 `.prev`。

資料庫不會自動覆寫成更新前備份。新版資料庫高於舊執行檔支援版本時，舊版會拒絕啟動，需由管理員評估相容版本或另行還原資料。保留資料庫連線設定與更新前備份，才能處理這種情況。

## 本機驗證

整合測試使用專用 PostgreSQL，Redis 與 NATS 也應使用獨立測試服務：

```sh
JELLY_TEST_POSTGRES=1 go test -race ./... -count=1 -timeout=2400s
JELLY_TEST_POSTGRES=1 JELLY_TEST_REDIS_URL=redis://127.0.0.1:56379 \
  JELLY_TEST_NATS_URL=nats://127.0.0.1:54222 \
  go test -race -tags nats ./internal/queue -count=1 -timeout=300s
```

`JELLY_TEST_POSTGRES`、`JELLY_TEST_ALLOW_LOOPBACK` 與 `JELLY_UPDATE_*` 測試接縫只用於本機驗收。正式環境不要設定測試旗標；其中 `JELLY_TEST_POSTGRES=1` 會讓部分背景端點同步執行，以便整合測試立即核對結果。
